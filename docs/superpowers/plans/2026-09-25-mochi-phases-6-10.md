# MoCHi Android Phases 6–10 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Extend the independent Phase 5 Android prototype through real-provider integration, attachments, voice contracts, local-first sync, and a defensible MoCHi Android product shell without modifying production MoCHi infrastructure or relying on the ChatGPT APK.

**Architecture:** Keep `ConversationCoordinator` provider-neutral and route provider execution through adapters. Store conversations and attachment metadata locally; keep binary files in application-managed storage. Add voice and sync as orthogonal services with deterministic local implementations and staging-only protocol tests. Product UI composes these boundaries without moving provider, credential, or sync wire types into the domain layer.

**Tech Stack:** Original Java 8 Android prototype, Android platform APIs, `HttpURLConnection`, Android Keystore/SharedPreferences, JSON/NDJSON/SSE codecs, Python standard-library staging servers, shell-based `javac`/AAPT2/D8 build scripts, and pure-Java contract tests.

## Global Constraints

- Execute Phases 6–10 continuously because the user explicitly authorized continuing past each phase gate.
- Preserve Phase 5 history and worktree; this branch starts from the pushed Phase 5 commit.
- Do not modify the official ChatGPT APK as an implementation strategy.
- Do not modify production MoCHi databases, Cloudflare resources, R2 data, provider credentials, authentication, billing, or Vercel configuration.
- Never store secrets in Git, Room/database records, messages, saved UI state, logs, reports, screenshots, APK resources, or committed BuildConfig.
- Keep provider-specific logic out of conversation models, UI, persistence, and coordinator state-machine logic.
- Keep provider execution separate from MoCHi cloud synchronization.
- Use local or isolated staging services and synthetic data for integration tests.
- Classify evidence as Confirmed, Inferred, Unknown, or Not tested; do not promote unavailable runtime evidence.
- Use original class names, schemas, UI, APIs, and assets.

## Review Focus

- A missing OpenRouter credential must leave local/mock/HTTP operation usable and must not leak a secret; test credential absence and redaction.
- A provider stream that terminates after partial content must preserve one stable assistant message and a normalized failure; test pre-content and post-content failure.
- An attachment whose source URI disappears must fail locally without deleting the draft or another message's file; test validation and cleanup ownership.
- A voice session interrupted by permission denial, audio focus loss, or lifecycle teardown must release resources and reach one terminal state; test repeated start/stop/error cycles.
- Sync retries, stale cursors, deletes, and quota failures must be idempotent and must not remove local data; test outbox replay and tombstone handling.
